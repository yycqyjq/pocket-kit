## 关键实现细节

### 乱码恢复的排序规则

「UTF-8 解码无替换字符的候选优先」——UTF-8 的字节结构是自校验的，
四个字节正好能按 UTF-8 解通，基本就说明原始字节就是 UTF-8。
之前按「类型加分」排序时，GBK 把 4 字节解成 2 个冷僻汉字反而得分更高
（每个汉字加 6 分），导致正确的 UTF-8 候选排到后面。用硬规则压住才修好。

### QP 的行尾空格

RFC 2045 规定空格和制表符可以原样写，但如果正好落在行尾就必须转义成 =20 / =09。
因为沿途的邮件系统会吃掉行尾空白。实现时要在 flush 行之前检查。

### BigInt 不支持 >>> 

UUID v1 的时间戳是 60 位，需要 BigInt 来避免精度丢失。
但 BigInt **没有无符号右移 `>>>`**——写成 `(BigInt(lo) >>> 0n)` 会直接抛 TypeError。
要先把 Number 转成无符号（`lo >>> 0`），再转 BigInt。

### 后行断言的兼容性风险

正则的后行断言 `(?<!…)` 是**解析期**特性。老一点的 Android WebView 不支持时
会让整段脚本直接语法错误——不是运行时问题，是解析都过不了。
所以 extract.js 的 16 个正则全部改用 `\b` 边界与捕获组，不用任何后行断言。
同理，`\p{P}` Unicode 属性转义（ES2018）也是解析期特性，也被替换掉了。

### 属性值里不能写 `\"`

在 `<PkRow value="...只有 & < > \" ' 需要转义..." />` 这种写法里，
HTML 属性中的 `\` 没有转义作用，Vite 会直接报
`Attribute name cannot contain U+0022 (")`。改用中文引号或换个说法。
**四个批次里一共踩了 4 次**。

### Base32 / TOTP 的官方向量

TOTP 是「错一位就全废」且用户看不出来的工具，所以必须对官方向量：
- RFC 4226：10 个 HOTP 计数器向量全过
- RFC 6238：6 个时间点（SHA-1）+ SHA-256 / SHA-512 各一个全过
- 空密钥报错、非法字符报错、otpauth:// 链接抽密钥、校验容错窗口

### 日期格式互转的实现思路

难点不是占位符映射（那只是数据表），而是**多词短语的匹配优先级**：
- `GROUP BY` 要在 `GROUP` 之前匹配，否则只匹配到 GROUP
- `LEFT OUTER JOIN` 要在 `LEFT JOIN` 之前，`LEFT JOIN` 又要在 `JOIN` 之前
- SQL 格式化里同理：`INSERT INTO` 要在 `INSERT` 之前，`DELETE FROM` 要在 `DELETE` 之前
- 但如果有**更短的**也合法（比如 `%d` 和 `%-d`），长的不一定优先——要看上下文

做法：每个记法的 token 表按长度降序排列，逐个尝试，找到第一个能完全匹配的就用。

### 文本抽取里会重叠的几类

- 手机号也是合法的长数字串（银行卡候选会抽到它）
- 18 位身份证同时满足银行卡长度要求
- 邮箱的域名部分也满足网址特征
这些都是格式本身的重叠，不是 bug。在界面上写清楚让用户只勾需要的即可。
