## 二、P0 —— 结果错误，用户直接可见

### P0-1　`workdaysBetween` 永远返回 0

**位置**：`src/utils/date.js:134`，调用处 `src/tools/components/ToolDateDiff.vue:129-130`

```js
export function workdaysBetween(a, b) {
  let from = Math.min(daysBetween(a, b), daysBetween(b, a))   // ← 问题在这
  const start = daysBetween(a, b) >= 0 ? a : b
  let count = 0
  for (let i = 0; i < from; i++) { ... }                      // from 恒为负 → 一次都不跑
  return count
}
```

`daysBetween` 是**带符号**的差值，`Math.min(d, -d)` 恒等于 `-|d|`（负数），
所以循环条件 `i < from` 永远不成立，`count` 恒为 0。

**复现**：`workdaysBetween(2026-09-01, 2026-09-30)` → `0`（应为 `21`）

**影响**：「日期推算」工具里"工作日"永远显示 0，"周末天数"显示全部天数 ——
`weekendDays: days - workdaysBetween(a, b)` 会把所有日子算成周末。

**修法**：

```js
const from = Math.abs(daysBetween(a, b))
```

（`start` 那行的判断本身是对的，不用动。）

### P0-2　`minifySql` 破坏 SQL 语义

**位置**：`src/utils/sqlfmt.js:298-301`

```js
export function minifySql(sql) {
  const r = formatSql(sql, { commaBreak: false })
  return r.text.replace(/\s*\n\s*/g, ' ').replace(/\s{2,}/g, ' ')
}
```

两个问题：

1. **`\s{2,}` → `' '` 会压缩字符串字面量内部的空格**
   `WHERE name = 'a  b'` → `'a b'`　—— 这是两个不同的查询条件。

2. **行注释 `--` 后面的换行被换成空格，导致其后所有 SQL 变成注释**
   ```sql
   -- 输入
   SELECT a FROM t WHERE x=1 -- 注释
   AND y IN (1,2,3) ORDER BY a DESC

   -- 压缩后（`--` 之后全部被注释掉）
   SELECT a FROM t WHERE x=1 -- 注释 AND y IN (1, 2, 3) ORDER BY a DESC
   ```
   执行时后半段条件与排序全部失效。

**影响**：「SQL 格式化」工具的「压缩」按钮。README 承诺"字符串、引号标识符与注释不会被破坏"，实际违反了。

**修法方向**：minify 不能对整段文本做正则压缩，要走 token 流 ——
字符串/引号标识符 token 原样输出；行注释要么删除、要么保留其后的换行。

### P0-3　`formatHtml` 压缩模式压坏 `<pre>` / `<script>` 内容

**位置**：`src/utils/codefmt.js:222-241`（minify 分支）

非压缩分支有 RAW_TAGS 保护：

```js
// codefmt.js:260 —— 非压缩分支，正确
if (RAW_TAGS.has(lastRawTag)) { cur += t.v; return }
```

但压缩分支漏了这一步，对**所有** text token 无条件做 `\s+` → `' '`：

```js
// codefmt.js:226-227 —— minify 分支，没有 RAW_TAGS 判断
if (t.t === 'text') {
  const collapsed = t.v.replace(/\s+/g, ' ')
```

**复现**：

| 输入 | 压缩后 | 期望 |
| --- | --- | --- |
| `<pre>  a   b\n    c</pre>` | `<pre>a b c</pre>` | pre 内空白原样保留 |
| `<script>var a = 1;  var b = 2;</script>` | `var a = 1; var b = 2;` | 保留（若 script 内含字符串则内容被改坏） |

**影响**：「代码美化」工具的「压缩」按钮。README 承诺"pre 内容不会被破坏"，实际违反了。

**修法方向**：minify 分支加 `if (RAW_TAGS.has(lastRawTag))` 判断，
pre/textarea/script/style 的内容原样输出（script/style 若要做真压缩需要单独的 JS/CSS 压缩器，不能只压空格）。

## 三、P1 —— 明确缺陷

### P1-1　`tokenizeHtml` 把属性值里的 `>` 当成标签结束

**位置**：`src/utils/codefmt.js:192`

```js
const j = s.indexOf('>', i)   // 不识别引号，取第一个 > 就当作标签结尾
```

**复现**：`<img src="a.png" alt="1 > 2">` → `alt="1 >\n2"`（被插入换行）。

HTML5 允许属性值里出现裸 `>`（`title="a > b"`、`onclick="if(a>b){}"` 都常见）。
属性值被切开后，多出来的部分会被当成文本节点重排。

**修法**：扫描标签时跟踪引号状态，遇到 `"` / `'` 进入引号内模式，
引号内不把 `>` 当结束符。

### P1-2　`cron.describe` 的汇总句忽略 日/月/星期 限制

**位置**：`src/utils/cron.js:201-211`

summary 只用 `hourArr` / `minArr` 拼接，完全没读 `dom` / `month` / `dow`：

```js
summary = '每天 ' + times.join('、') + ...
```

**复现**：

| 表达式 | summary（错） | 同返回值分项 | 应为 |
| --- | --- | --- | --- |
| `0 9 * * 1-5` | 每天 09:00 | 星期：**工作日** | 工作日 09:00 |
| `0 9 1 * *` | 每天 09:00 | 日：1 | 每月 1 号 09:00 |

同一个返回值里汇总句与分项自相矛盾。

### P1-3　`datefmt` 单字符占位符转换错误

**位置**：`src/utils/datefmt.js`

Java 的 `M` / `d` / `H` / `m` / `s` 是"无前导零"写法，转换到其他记法时出错：

| 输入 | 输出 | 应为 |
| --- | --- | --- |
| strftime | `%Y-M-d H:m:s` | `%Y-%-m-%-d %-H:%-M:%-S` |
| Go | `2006-M-d H:m:s` | `2006-1-2 15:4:5` |
| moment | `YYYY-M-d H:m:s` ✅ | 正确 |

注意 strftime 里 `%M` 是**分钟**、`%m` 是**月份**，所以裸 `M` 会被当字面量输出 ——
工具给出的 sample 也确实显示成 `2026-M-d H:m:s`。用户能看出不对，但 pattern 本身是错的。

### P1-3 展开：datefmt 的问题比报告里写的更深

报告只写了「单字符占位符转换错误」，实际排查出三层：

1. **缺 token**：`render` 表产出 `M` / `d` / `D` / `DDD` / `002`，但 `tokens` 表里没有对应条目
   → 译回来的格式串把它们当字面量。往返矩阵探针一次抓出 **9 处**（java 3、moment 3、go 3）。
2. **顺序依赖**：`parsePattern` 靠手写数组顺序保证「长 token 优先」。这很脆弱 ——
   补进单字符 `1` 后，Go 的 `15`（小时）会被拆成 `1`+`5`。
   改为**按长度降序匹配**，从机制上消除这类地雷。
3. **补零语义丢失**：Java 的 `H:m:s` 在 14:05:09 输出 `14:5:9`，而 `renderSample` 一律补零
   → 示例值是错的。新增 `hour24n` / `hour12n` / `minuten` / `secondn` / `dayOfYearn`
   五个「不补零」类型，并在 `convert` 里做**双向兜底**（某记法缺某变体时退回另一变体，
   而不是让字段变成空串）。

`%-H` / `%-I` / `%-M` / `%-S` 先在本机 C 库实测可用，才敢拿它们做 strftime 的不补零写法。

#### ① 浅色模式输入框占位符对比度 2.35:1 → 5.03:1

**根因**：`App.vue` 的 `.pk-ph` 规则把占位符颜色**硬编码**成 `#98a29c`。
这个值原本等于旧版 `--pk-text-3`，后来 `--pk-text-3` 为通过对比度检查被加深到 `#68736d`，
硬编码的那份没跟着走，于是掉了队 —— 而且占位符底色是 `--pk-input`（`#f4f2ec`），
比卡片白底更深，对比度雪上加霜。

**改法**：新增独立变量 `--pk-ph`，不再借用 `--pk-text-3`，也不硬编码。

| 主题 | 变量值 | 所在底色 | 对比度 |
| --- | --- | --- | --- |
| 浅色 | `#5f6a64` | 输入框 `#f4f2ec` | **5.03** |
| 浅色 | `#5f6a64` | 首页搜索框（白卡片） | **5.63** |
| 深色 | `#8f9993` | 输入框 `#262d32` | **4.75** |
| 深色 | `#8f9993` | 首页搜索框 `#1d2226` | **5.46** |

同时删掉了 `.theme-dark .pk-ph { color: #6f7873 }` 那条硬编码覆盖（原值只有 3.07:1）。

**实测**：新写 `t12-placeholder.mjs`，覆盖 50 个工具 + 首页、浅色/深色各扫一遍（共 102 次页面加载）。
捕获到占位符元素的真实 class 是 `uni-input-placeholder pk-ph` —— 确认 `placeholder-class="pk-ph"`
确实作用到了占位符元素上、变量继承链是通的。**6/6 组合全部 ≥4.5:1**。

> 教训：主题变量化改造要**连带清掉所有硬编码副本**。只改变量、不改硬编码，

#### ② 工作日统计的区间口径：半开 → 含首尾

**问题**：`daysBetween` 是半开区间（不含结束日），所以 `9/1 → 9/30` 显示 29 天。
技术上自洽，但「9月1日到9月30日」按直觉是 30 天，用户看到 29 会以为算错了。

**改法**：两种口径**都保留**，把两种问法分开，而不是二选一。

- `date.js` 的 `workdaysBetween` 新增 `opt.inclusive` 选项。
  默认 `false` 维持半开 `[a, b)`；`true` 走闭区间 `[a, b]`。
- `ToolDateDiff.vue` 改为 span/gap 双口径：
  - **共几天（含首尾）** = `span` —— 主口径，回答「这段时间有几天」
  - **相隔天数（不含结束日）** = `gap` —— 回答「隔了多久」
  - 工作日/休息日改按**含首尾**计算，两者之和**恰好等于 `span`**

| 场景 | 共几天 | 相隔天数 | 工作日 | 休息日 | 合计 |
| --- | --- | --- | --- | --- | --- |
| 9/1 → 9/30 | 30 | 29 | 22 | 8 | 22 + 8 = 30 ✓ |
| 同一天（9/20 周日） | 1 | 0 | 0 | 1 | 0 + 1 = 1 ✓ |
| 2026 全年 | 365 | 364 | 261 | 104 | 261 + 104 = 365 ✓ |

> 改之前是「29 = 21 + 8」，三个数字单看都对，但凑一起就不像在说同一件事。
> 改成闭区间后「工作日 + 休息日 = 共几天」成了恒等式，用户可以自己验算 —— 这比数字本身更重要。

**实测**：新增 `t13.mjs`（10 项口径断言，含 11 组跨度的恒等式对账、与 `isWeekend` 逐日暴力对账）
和 `t14-datediff.mjs`（23 项 UI 断言，含同一天、反序、跨整年、非法输入四个场景）。

#### ③ 删除 `datefmt.js` 顶部零引用的 `const T`

一张 22 项的字段类型中文标签表，**全项目零引用** —— 真正干活的是 `ToolDatefmt.vue` 里的 `TYPE_CN`。
留着它是陷阱：看着像权威映射表，改字段类型时容易被误改（改完不生效，还会误导后来人）。
已连同上方注释一并删除，`grep` 复核零残留。

## 第三轮修复（2026-09-20 深夜）：设计 token 与组件库收口

### ① 语义色 token 化（修 P2-3 硬编码项）

19 个工具组件在 `<style>` 与 `PkRow color=` / `PkCard accent=` 里硬编码了 `#3F7A6E`/`#B4553E`/`#A8642F`，

| --- | --- | --- |

### ② 主按钮白字（修 P2-3 白字项）—— 新增 `--pk-on-accent`

根因：`--pk-accent` 在深色下提亮到 `#6BB3A3` 是为了当**文字**够亮，但同一个亮绿托不住白字（2.44）。
一个 token 无法同时满足「够亮做文字」和「够暗托白字」，故拆出 `--pk-on-accent`（浅 `#fff` / 深 `#101418`），
`.pk-btn--primary` 文字引用它 → 深色 **2.44 → 7.58**，浅色观感不变。

### ③ 原生取色点：`theme.js` 导出 `themeColors` 镜像

`uni.showModal` 的 `confirmColor`、`<switch>` 的 `color` 不解析 CSS 变量，在 `theme.js` 留了一份
响应式 JS 镜像（`SEMANTIC_LIGHT` / `SEMANTIC_DARK`），`PkSwitchRow` 与首页两处 `confirmColor` 改绑它。
注释标明须与 `App.vue` 的 token 同步 —— 深色下开关/弹窗按钮不再停在浅色绿。

### ④ 抽出 `PkOutput` 组件（结构层收口，非仅样式）

`.out` 输出框被 13 个工具逐字手抄了 **15 处**（含 26 个重复样式块）。抽成 `src/components/PkOutput.vue`，
用 `mono` / `pre` / `size` 三个 prop 覆盖全部差异。其余只出现 1 次的工具边框属专属排版，**不抽**（避免单点伪组件）。

### ⑤ 描边粗细单一来源：`--pk-line-w`（定 1px）

`--pk-line-w` 收口「描边多粗」。公共组件 7 处 + 工具层 54 处（33 文件）原先各自写死 `1px`、且导航用 `scaleY(0.5)`，
现全部走该 token。定值取 **1px**（0.5px 在桌面 DPR=1 预览偏淡，1px 跨设备最稳）。

### ⑥ easycom 自动注册（组件库管理层）

`registry.js` 里 Tool 组件的显式 import（喂 `<component :is>` 动态映射）**保留不动**。
